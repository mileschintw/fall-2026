1. 2D index、邊界與 blur 的結構

Index 公式（L2 p13）：

col = blockIdx.x * blockDim.x + threadIdx.x;   // x 是水平方向，移動最快
row = blockIdx.y * blockDim.y + threadIdx.y;   // y 是垂直方向
offset = row * width + col;                    // row-major 攤平成 1D
  • Host 端 dim3 的順序是 (x, y, z)，所以 grid 的 x 方向對應寬度（欄數），y 對應高度。L2 p17 把這兩個寫反了，p26 才是對的。
  • Grid 大小用 ceil-div：(width + bx - 1) / bx。多出來的 thread 一定要擋掉。老師的例子是 62×76 影像配 16×16 block，grid 是 4×5，共 64×80 個 thread。
  • Kernel 裡的 a[i][j] 語法不能用，因為 host 傳來的是 1D buffer，要自己算 offset。

兩層邊界檢查（L2 p22–p23）：

  • 第一層：這個 thread 的輸出位置有沒有在影像內。沒有就不要處理。
  • 第二層：鄰域裡的每個 pixel 有沒有在影像內。超出的就跳過，而且不能算進分母。
  • 只讀資料可以被很多 thread 重疊讀取沒有問題；每個 thread 只寫自己的輸出 pixel，所以不需要同步，也沒有 race。

Box blur 的結構（課堂版本）：對輸出位置 (row, col)，雙層迴圈走過 [-r, r]²，每個在範圍內的鄰居累加 pixel 值並計數，最後用「累加 ÷ 計數」寫回。

HW2 的 Gaussian 和 box blur 差在哪（spec 5b）：

  • 濾波器是提供的 9×9 float 係數，所以半徑 r = 4。係數的 index 要由鄰居的偏移量換算成 0..80 的一維位置。
  • 每個「係數 × pixel」先四捨五入成 int，再用 32-bit int 累加，避免 overflow。
  • 正規化改成除以實際用到的係數總和（只算在影像內的鄰居），不是除以 pixel 數。
  • 最後轉回 unsigned char 寫出。除法後怎麼捨入，spec 沒有規定，自己決定並在報告寫明。
  • 輸入是 8-bit 單色，host 和 device 都用 unsigned char；用 stb_load() 回傳的寬、高、channel 數確認是單色。

建議先做 CPU 版本當 reference。整數運算加固定的捨入規則，CPU 和 GPU 應該可以逐像素完全相同；如果不同，通常是邊界或捨入規則不一致。

2. 記憶體階層與 shared memory

種類宣告誰看得到存活多久速度
register一般區域變數單一 threadthread最快
localper-thread 陣列、register 溢出單一 threadthread很慢（實際在 global）
shared__shared__同一個 blockblock快（SM 上的 SRAM）
global__device__、cudaMalloc整個 grid，host 也能存取整個 application慢（DRAM）
constant__constant__整個 grid，唯讀整個 application有 cache，容量小
  • Shared memory 是 scratchpad：宣告、搬入、使用都要自己寫，不會自動快取。每個 block 看不到別的 block 的 shared memory。
  • Static：kernel 內 __shared__ float name[SIZE];，大小必須是編譯期常數。
  • Dynamic：kernel 內 extern __shared__ float name[];，大小由 host 在 launch 的第三個參數給（bytes）：kernel<<<grid, block, sharedBytes>>>(...)。
  • 合作搬移（L3 p47）：block 內的 thread 先算出自己在 block 裡的線性編號（2D block 要用 threadIdx.y * blockDim.x + threadIdx.x），從這個編號開始，每次前進「block 內 thread 總數」，直到蓋完所有係數。這樣不管 block 大小比係數個數大或小都能搬完。spec 寫「前 N 個 thread」，block 小於 N 時就需要這個走法。
  • 搬完一定要 __syncthreads()，否則有 thread 可能在資料還沒到位時就開始讀。

最容易犯的錯：__syncthreads() 是 block 範圍的 barrier，block 內所有 thread 都要執行到，否則 deadlock 或未定義行為。影像邊緣的 block 有一部分 thread 在影像外。不要在 __syncthreads() 之前就讓這些 thread return。順序是：搬係數 → 同步 → 才檢查「我在不在影像內」。

要多一個 kernel 參數把係數陣列（在 global memory）傳進來。三個版本的差別只在「讀係數的來源」：直接讀 global，或讀 shared 的副本（static / dynamic）。

3. Warp 與硬體資源（步驟 12 的 QUESTION）

  • Block 切成 warp：32 個連續 thread 一組，2D block 先以 x 最快的順序攤平再切。Warp 數 = ceil(block 的 thread 數 ÷ 32)。不滿 32 的補 inactive thread。
  • SM 同時能放多少 block、多少 thread 有上限，block 數量遠大於此時，分批排進 SM（wave）。
  • T4（作業題目問的，L2 p38–p44）：40 個 SM，每 SM 最多 16 個 block、1024 個 thread，每個 processing block 16 個 FP32 core。
  • 你的 RTX 3050（本機 devicequery 實測）：20 個 SM，每 SM 最多 16 個 block、1536 個 thread，CC 8.6，shared memory 每 SM 100 KB。

回答「幾個 warp 在跑」的推理框架（答案自己算）：

  1. 從 Warp Info 視窗直接數出實際看到的 warp 數。
  2. 算 launch 設定：總 block 數、每個 block 幾個 warp。
  3. 對照 SM 數和每 SM 的 block／thread 上限，推出同一時間「最多能有多少 block 常駐」。
  4. debugger 停下來時，是被排進 SM 的那一批在執行，不是整張影像全部同時在跑。
  5. 報告裡兩個 GPU 都寫：題目指定的 T4 規格，以及你實際使用的 3050 規格。

4. Arithmetic intensity 與 roofline（P1、P2）

AI = W ÷ Q（FLOPs ÷ bytes）。老師說這是這門課「可能最重要的指標」（L3 [01:16:00]）。

  1. 寫出演算法的式子，一個輸出元素是怎麼算出來的。
  2. 算 W：每種運算各自數出來，分項寫。FMA = 2 FLOP，transcendental（exp、tanh、erf、sqrt）= 4 FLOP，其餘乘、加、減、比較各 1。
  3. 算 Q = Q_read + Q_write：只算 global memory。每個項寫成「元素個數 × bytes 每個元素」。FP32 是 4 bytes，一定要乘（老師特別提醒過）。Register 與 cache 流量當作免費（perfect cache 假設）。
  4. AI = W ÷ Q，化簡成 N 的函式，並檢查合理範圍。老師說大多數演算法落在 0.1 到幾百之間，超出就該回頭檢查。
  5. 表格欄位照 spec：algorithm | FLOPs | Mem bytes | AI，分子分母的每一項都要列出來。

老師現場算的例子：FP32 方陣 GEMM（C = AB）：W = 2N³（N³ 次 FMA，每次 2），Q_r = 2·N²·4、Q_w = N²·4，所以 Q = 12N²，AI = N/6。SGEMV 約 1/2，DGEMV 約 1/4。

投影片 p36 寫成 N/3D（FP32 時 D=4，等於 N/12），差在 W 有沒有乘 2。依老師口頭，W = 2N³。HW2 的 P1 寫 FLOPs 時，把「乘和加各算一個 FLOP」寫清楚。

題目細節：P1b 是 3-pass、unfused。unfused 的意思是每個 pass 各自把資料讀進來、寫回去，pass 之間的中間結果要經過 global memory。P1b 沒有給輸入大小，自己定義變數（例如長度或 batch×維度）。

Roofline（L3 p29–p31）：

  • 可達效能 P = min(peak compute, β × AI)，β 是 peak memory bandwidth。
  • Ridge point = peak compute ÷ β，單位 FLOP/byte。AI 在左邊是 memory-bound，在右邊是 compute-bound，靠近 ridge 是 transitional。「靠近」怎麼定義，自己訂一個門檻（例如 ridge 的 0.5×–2×）並寫明。
  • Log-log 圖上，斜線段的斜率永遠是 1。
  • 必須把 P1 的 3 個 AI 代入具體數值再畫，並寫出用了哪些值。換一組值可能換 regime。
  • 用 FP32 非 tensor 的 peak 值，與 P1 一致。

5. Tiling 與 Q1–Q3 的觀念

  • 為什麼 tiling 有效：在一個 block 內，每一列 M、每一行 N 會被不同的 thread 重複讀 TILE_WIDTH 次。把它們先搬進 shared memory，後面重複使用，global memory 流量減少 TILE_WIDTH 倍，AI 變成 TILE_WIDTH/4。
  • Phase：把 dot product 拆成多段，每段是一個 phase，分成 LOAD（每個 thread 搬一個 M 元素和一個 N 元素進 shared）與 USE（用 shared 的 tile 算部分和）。
  • 兩次同步：LOAD 後一次（read-after-write，載入完才能用）；USE 後一次（write-after-read，這一輪用完才能讓下一個 phase 覆寫）。
  • 輸出要等所有 phase 做完，才從 register 寫回 global 一次。

Q1、Q2、Q3 各自該想的事（不給答案）：

  • Q1：shared 變數的 scope 與 lifetime 是什麼單位？題目給了 block 數和每 block 的 thread 數，哪個數字和「份數」有關？
  • Q2：L3 的結論是 tiling 使 global 存取減少「幾倍」，與 tile 的哪個尺寸有關？「使用量減少到原來的幾分之幾」是同一件事的倒數。
  • Q3：先算一個 32×32 單精度 tile 共幾 bytes，再除以題目給的 DRAM burst 大小。這題只是一個除法，但要在答案中寫出步驟。

6. Host 端計時（步驟 6–7）

用 profileapi.h 的 QueryPerformanceCounter 與 QueryPerformanceFrequency（解析度小於 1 µs）。基本寫法：

LARGE_INTEGER freq, t0, t1;
QueryPerformanceFrequency(&freq);
QueryPerformanceCounter(&t0);
// ... 被量的工作 ...
QueryPerformanceCounter(&t1);
double ms = (t1.QuadPart - t0.QuadPart) * 1000.0 / freq.QuadPart;
  • Kernel launch 是非同步的。停止計時前要 cudaDeviceSynchronize()，否則量到的只是 launch 的時間。
  • 老師建議量兩種：單獨的 kernel 時間，以及包含 HtoD、kernel、DtoH 的完整 round-trip。與 CPU 比較時，round-trip 通常更有意義。
  • Starter 裡已有註解標出 start/stop 的位置，照放即可。
  • DEBUG 與 RELEASE 各量 4 張影像，不要在 debugger 裡跑。每個 timer、每張影像的結果都存下來。
  • 第一次呼叫 CUDA 會建立 context，若編的是 sm_75，在 3050 上還會 JIT。第一次的數字可能偏大，建議先做一次 warm-up 呼叫，或在報告註明。

  • 26a：這個作業只有「濾波器係數」放在 shared memory，影像本身仍從 global 讀。81 個 float 很小，而且所有 thread 反覆讀同一批值，在硬體上很可能本來就被 cache 住。所以 shared 版不一定比較快：它多了搬移、同步和額外指令。回答時比較三項數據：execution time、instruction 數、dram bytes，並從記憶體型別的特性解釋差異（或沒有差異）。不要預設答案，以量到的為準。

編譯設定

sm_75 在 RTX 3050 上會有問題嗎

不會有問題。HW1 就是這樣跑的，而且 local-runbook.md 已實測：

  • VS 預設 compute_75,sm_75 會同時嵌入 sm_75 的 SASS 和 compute_75 的 PTX。3050 是 CC 8.6，跑不了 sm_75 的 SASS，driver 會把 PTX 即時編譯（JIT）成 sm_86 的版本來執行，並快取。實測在 driver 617.42 可以。
  • 相反方向才會出錯：只編 8.0 拿到 7.5 的 T4 上跑會出現 no kernel image is available（L2 [00:43:21]）。
  • runbook 也實測過 -gencode arch=compute_75,code=sm_75 -gencode arch=compute_86,code=sm_86 的雙目標編法，結果一樣。

HW2 的建議：改用 compute_86,sm_86

HW2 要量時間、要 profile、要用 debugger，原生的 sm_86 比 JIT 乾淨：

  • 計時：JIT 的成本（通常幾秒）出現在第一次 launch，會污染第一個 timer 的數字。
  • NCU：profile 的是 JIT 出來的程式碼。雖然也是 sm_86 的機器碼，但原生編譯更直接，也省掉每次新 exe 第一次執行的 JIT 時間。
  • Debugger：L2 [03:24:03] 說除錯時編譯目標要和裝置相符，否則 kernel 不會跑。那是針對 T4 的說法，在 3050 上對應的是 8.6。

設定位置：Project Properties → CUDA C/C++ → Device → Code Generation，填 compute_86,sm_86。想保留相容性可以填 compute_75,sm_75;compute_86,sm_86。

spec 寫「設 sm_75 對應 T4」，那是為了 AWS 的 T4。你在 3050 上，設成 sm_86 沒有違反作業目的。報告中寫明「使用本機 RTX 3050（CC 8.6），編譯目標 sm_86」，以及它和 T4 的差異（SM 數、每 SM 的 thread 上限、記憶體頻寬）。NCU 數值會和 T4 不同，這是預期的。

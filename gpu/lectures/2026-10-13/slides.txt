Data Dimensionality: 
application view and computer view 
   An application domain expert may think of the data for a problem in its 
“natural” dimensionality 
   image processing: 2D h( x,y ): e.g. images 
   physical problem: 3D f( x,y,z ) : e.g. physical volumetric space 
   However, computer memory space is a “flat” address space. 
   the compiler and processor reference memory using a base + offset 
   1D linear, contiguous 
   Thus, all higher - dimensional data representations are ultimately “linearized” 
   “flattened” into equivalent 1D arrays 
   multi - dimensional indexing syntax translated into 1D offsets 
   consider: c - style multi - dimensional arrays 
   x[i][j] 
   y[i][j][k] 
   * note left - most index is “slowest moving”, right - most is “fastest”

Recall: Little - endian representation 
   When you look at multi - byte values (float32, int32, double) in memory on an 
Intel x86 / x64 architecture the values are stored in   little - endian   form 
   Byte Order:   The bytes are ordered from the smallest part of the number to the 
largest part. 
   Example:   Take the 4 - byte hexadecimal number   0x12345678   (where   0x12   is the most 
significant byte and   0x78   is the least significant byte). 
   In Memory:   A   little - endian   system stores the bytes in reverse order across 
sequential memory addresses: 
   Address   0x00 :   0x78 
   Address   0x01 :   0x56 
   Address   0x02 :   0x34 
   Address   0x03 :   0x12

void   blurKernel ( unsigned   char   * in,   unsigned   char   * out,   int   w,   int   h, int BLUR_SIZE) { 
int   Col =   blockIdx.x   *   blockDim.x   +   threadIdx.x ; 
int   Row =   blockIdx.y   *   blockDim.y   +   threadIdx.y ; 
if   (Col < w && Row < h) { 
int   pixVal   =   0 ; 
int   pixels =   0 ; 
// Get the average of the surrounding 2xBLUR_SIZE+1 x 2xBLUR_SIZE+1 box 
for ( int   blurRow   =   - BLUR_SIZE;   blurRow   < BLUR_SIZE+1; ++ blurRow ) { 
for ( int   blurCol   =   - BLUR_SIZE;   blurCol   < BLUR_SIZE+1; ++ blurCol ) { 
int   curRow   = Row +   blurRow ; 
int   curCol   = Col +   blurCol ; 
// Verify we have a valid image pixel 
if   ( curRow   >   - 1 &&   curRow   < h &&   curCol   >   - 1 &&   curCol   < w) { 
pixVal   += in[ curRow   * w +   curCol ]; 
pixels++;   // Keep track of number of pixels in the accumulated total 
} 
} 
} 
// Write new pixel value out 
out[Row * w + Col] = ( unsigned   char )( pixVal   / pixels); 
}

SIMD versus SIMT 
SIMT = Single Instruction Multiple   Threads   (NVIDIA term) 
Both models run one instruction over many ALU lanes at once. 
They differ in   what the programmer writes   and   what the hardware automatically 
CPU SIMD 
the   vector   is the unit of programming: 
one thread issues instructions on wide registers, 
programmer (or compiler) explicitly manage width, masking, and data layout. 
NVIDIA’s SIMT 
the   scalar thread   is the unit of programming: 
programmer declares independence of   cuda   kernel threads, 
the hardware groups 32 threads into a   warp   that runs on SIMD lanes. The 
hardware implicitly handles masking, divergence, per - lane addressing, and 
latency hiding at run time.

Warps as Scheduling Units 
•   Each Block is executed as   32 - thread Warps 
–   Once a block is assigned to an SM, it is divided into 32 - thread warps. 
–   An implementation decision, not part of the CUDA programming model

–   Partial warps padded with inactive threads 
–   Future GPUs may have different number of threads

ThreadBlock   Granularity Considerations 
–   For kernels using multiple blocks, should each block 
have 4X4, 8X8 or 30X30 threads for Volta? 
–   NOTE: Each Volta SM can take up to 2048 threads, 32 blocks 
▪   For 4X4, we have 16 threads per Block. 
▪   Each SM can take up to 2048 threads: 2048/16 =128 Blocks. 
▪   But each SM can only take up to 32 Blocks, 
▪   so only 16*32 = 512 threads will go into each SM.   512/2048 = 25% utilization 
▪   For 8X8, we have 64 threads per Block. 
▪   Since each SM can take up to 2048 threads, it can take up to 32 Blocks 
▪   Thus 32*64 = 2048 
▪   achieves full capacity   (unless other resource considerations overrule). 
▪   For 30X30, we would have 900 threads per Block. 
▪   Only two blocks could fit into an SM for Volta, 
▪   1800/2048 ~= 88% of the SM thread capacity would be utilized.

NEW: Thread Block Clusters (TBCs) 
   H 100   introduces a new thread block cluster architecture that exposes control of locality at 
a granularity larger than a single thread block on a single SM. 
   TBCs add another level to the GPU ’ s physical programming hierarchy to include threads, 
thread blocks, thread block clusters, and grids. 
   TBC is a group of thread blocks that are guaranteed to be concurrently scheduled onto a 
group of SMs, where the goal is to enable efficient cooperation of threads across multiple 
SMs. 
   The clusters in H 100   run concurrently across SMs within a GPC. 
   A   GPC   is a group of SMs in the hardware hierarchy that are always physically close 
together. Clusters have hardware - accelerated barriers and new memory access 
collaboration capabilities

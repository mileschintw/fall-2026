Why Kernel 3 stalls: 2 shared loads per FMA 
M O T I V A T I O N 
// Kernel 3 inner loop (per thread, one output) 
for   ( int   dotIdx =   0 ; dotIdx < BLOCKSIZE; ++dotIdx) { 
tmp += As[threadRow * BLOCKSIZE + dotIdx] * 
Bs[dotIdx * BLOCKSIZE + threadCol]; 
} 
// what the compiler emits (PTX, per iteration) 
ld.shared.f32   %f91, [%r8+3456];   // As 
ld.shared.f32   %f92, [%r7+108];   // Bs 
fma.rn.f32   %f93, %f92, %f91, %f90; 
Instructions per fused multiply - add 
Kernel 3   1 FMA   2 LDS 
Kernel 4 (TM = 8)   1 FMA   1.125 LDS 
Shared - memory loads (LDS) are not free: they queue in the SM’s memory - I/O pipe. 
The profiler shows Kernel 3 warps mostly in “Stall MIO Throttle”: waiting for that 
queue. 
The idea of Kernel 4 
•   Give each thread TM = 8 outputs stacked in one 
column of the tile. 
•   For each k - step, load one B value into a register 
(tmpB) and reuse it for all 8 FMAs. 
•   Keep the 8 running sums in registers 
(threadResults[8]), not in shared memory. 
•   Loads per FMA drop from 2 to 9/8; the block tile 
grows to 64   ×   64 with a thinner K - slice (BK = 8), 
so shared memory per block shrinks to 4 KB. 
Also known as:   thread coarsening, register tiling, 1 - 
D thread tiling.

Grid:   64   ×   64 = 4,096 blocks, each owning a 64   ×   64 tile

Per block:   512 threads = 16 warps; each thread owns 8 
outputs (a 1   ×   8 column strip). 
Outer loop:   K/BK = 4096/8 = 512 iterations. 
Each stages As (64 × 8)   ( BMxBK )   and Bs (8 × 64)   ( BKxBN )   =

Kernel 3 for comparison:   32 × 32 tile, BK = 32, 8 KB per 
iteration, 65,536 FLOPs = 8 FLOP/B. 
Assumption in the code:   M, N, K are multiples of the tile 
sizes (no bounds checks).

A loads: 4 short rows 
A warp covers 4 rows of A, 8 consecutive floats each (32 
B, one full sector per row): 4 sectors, 100% used, but 4 
separate cache lines. 
B loads: one contiguous row 
A warp reads 32 consecutive floats of one row of B: 128 B 
in one line, 4 sectors, the ideal case from the last lecture. 
Why two index pairs? 
As has 64 × 8 = 512 entries and Bs has 8 × 64 = 512: exactly 
one per thread. 
The code asserts BM·BK ==   blockDim.x   and BN·BK == 
blockDim.x . 
Loading and computing partition the same 512 threads in 
different shapes.

Boehm’s L2   Cache behavior   remark 
Blocks are scheduled roughly in   blockIdx   order. 
Consecutive   blockIdx.x   values (colored) share the same 
slab of A and read adjacent slabs of B. 
Swapping x and y cost about 30% for large matrices: the 
concurrently running blocks then share columns of A but 
touch B non - sequentially, lowering the L2 hit rate. 
Lesson:   the   block→tile   mapping is itself a locality 
decision. 
Reading the pointer moves:   A[r][c] lives at A[r·K + c], so “down 64 rows” is +64·K floats 
and “right 8 columns” is +8. B[r][c] lives at B[r·N + c], so “down 8 rows” is +8·N. After the 
moves, A[innerRowA·K + innerColA] and B[innerRowB·N + innerColB] address the current 
K - slice directly.

Source, part 2: the main loop and the write - out 
P A R T 2 · S O U R C E L I S T I N G 
// outer loop over block tiles 
for   ( uint   bkIdx =   0 ; bkIdx < K; bkIdx += BK) { 
// populate the SMEM caches 
As[innerRowA * BK + innerColA] = A[innerRowA * K + innerColA]; 
Bs[innerRowB * BN + innerColB] = B[innerRowB * N + innerColB]; 
__syncthreads(); 
// advance blocktile 
A += BK; 
B += BK * N; 
// calculate per - thread results 
for   ( uint   dotIdx =   0 ; dotIdx < BK; ++dotIdx) { 
// we make the dotproduct loop the outside loop, which facilitates 
// reuse of the Bs entry, which we can cache in a tmp var. 
float   tmpB = Bs[dotIdx * BN + threadCol]; 
for   ( uint   resIdx =   0 ; resIdx < TM; ++resIdx) { 
threadResults[resIdx] += 
As[(threadRow * TM + resIdx) * BK + dotIdx] * tmpB; 
} 
} 
__syncthreads(); 
} 
// write out the results 
for   ( uint   resIdx =   0 ; resIdx < TM; ++resIdx) { 
C[(threadRow * TM + resIdx) * N + threadCol] = 
alpha * threadResults[resIdx] + 
beta * C[(threadRow * TM + resIdx) * N + threadCol]; 
} 
}

SMEM loads per FMA 1.125 → 0.25; 
GMEM loads per output K/32 → K/64; 
block intensity 16 → 32 FLOP/B.

Registers are the budget 
80 live floats per thread; 
__launch_bounds__ and full unrolling 
keep them in registers; occupancy falls 
to ≈ 33% and ILP covers it.

Next lever: instructions 
The bytes are now cheap; vectorizing 
loads and transposing As (Kernel 6)

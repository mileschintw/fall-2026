PART 1 · SRAM BASICS 
SRAM vs. DRAM: different bottlenecks 
On - chip SRAM (registers, L1/SMEM, L2)   Off - chip DRAM (global memory, L5) 
Read   Non - destructive; no row to open   Destructive; open a row, then restore 
Parallelism   32 banks per SM, every cycle   Channels   ×   banks across chips 
Address → bank   Simple: word index mod 32   Hashed across channels and banks 
Costly pattern   Lanes hit one bank, different words: bank conflict   Scattered addresses: row misses, wasted sectors 
Fix   Padding, swizzling, broadcast   Coalescing, streaming access 
On our T4:   96 KB of SRAM per SM, split between L1 and shared memory (32 or 
64 KB SMEM). 32 banks   ×   4 B = 128 B per cycle per SM.

=== p36 ===
SMEM: Takeaways 
   SMs have combined L1 Data Cache and Shared Memory units 
   Common physical data memory 
   Common overall basic performance characteristics 
   Very different optimization strategies! 
   Consider Shared Memory, when … 
   Accessing subset of data multiple times within block 
   Using data synchronization across threads/warps of a block 
   Cooperative parallel algorithms within threads/warps of block 
   Benefiting from user - managed cache, i.e. you are in charge what is stored for how long 
   Requiring memory access pattern that do not fit well to L1 Cache Sectors or Cache Lines 
   ‘Diagonal’ accesses in memory banks 
   Sweet spots of   strided   accesses with no bank conflicts 
   Reducing or improving global memory traffic through L2 
   Use shared memory atomics for local reductions = less global atomics 
   Shared atomics have higher throughput than global L2 atomics

__global__ void   transposeCoalesced (float*   odata , 
const float*   idata , int rows, int cols) 
{ 
__shared__ float tile[TILE_DIM][TILE_DIM];   // 32 x 32 
int x =   blockIdx.x   * TILE_DIM +   threadIdx.x ; 
int y =   blockIdx.y   * TILE_DIM +   threadIdx.y ; 
for (int j = 0; j < TILE_DIM; j += BLOCK_ROWS)   // (1) 
tile[ threadIdx.y   + j][ threadIdx.x ] = 
idata [(y + j) * cols + x]; 
__ syncthreads ();   // (2) 
x =   blockIdx.y   * TILE_DIM +   threadIdx.x ;   // (3) 
y =   blockIdx.x   * TILE_DIM +   threadIdx.y ; 
for (int j = 0; j < TILE_DIM; j += BLOCK_ROWS)   // (4) 
odata [(y + j) * rows + x] = 
tile[ threadIdx.x ][ threadIdx.y   + j];   // column! 
} 
1   Load phase: warp = one tile row 
The warp reads 32 consecutive floats of A (coalesced) and 
writes tile row r: banks (32r + x) mod 32 = x   —   all distinct, 
conflict - free. 
2   The barrier is required 
BLOCK_ROWS = 8, so a thread later reads tile entries that 
other warps wrote. 
3   Swap blockIdx, not threadIdx 
The output tile position is transposed; threadIdx.x stays the 
fastest - varying index so the global store still coalesces. 
4   Store phase: warp = one tile column 
threadIdx.y is constant across the warp and threadIdx.x = 
0…31, so the warp reads tile[0..31][c]: 32 words, one bank.

__global__ void   transposeNoBankConflicts (float*   odata , 
const float*   idata , int rows, int cols) 
{ 
__shared__ float tile[TILE_DIM][TILE_DIM   + 1 ];   // 32x33 
int x =   blockIdx.x   * TILE_DIM +   threadIdx.x ; 
int y =   blockIdx.y   * TILE_DIM +   threadIdx.y ; 
for (int j = 0; j < TILE_DIM; j += BLOCK_ROWS) 
tile[ threadIdx.y   + j][ threadIdx.x ] =   // row write 
idata [(y + j) * cols + x]; 
__ syncthreads (); 
x =   blockIdx.y   * TILE_DIM +   threadIdx.x ; 
y =   blockIdx.x   * TILE_DIM +   threadIdx.y ; 
for (int j = 0; j < TILE_DIM; j += BLOCK_ROWS) 
odata [(y + j) * rows + x] = 
tile[ threadIdx.x ][ threadIdx.y   + j];   // column read 
} 
1   The entire fix is one token 
+ 1   adds a 33rd word to every row. No index expression 
changes; 
the compiler multiplies the row index by 33 instead of 32. 
2   What changed in the address math 
word( i , j) =   33·i   + j, 
so bank( i , j) = ( i   + j) mod 32 
the row index now moves the bank. 
3   Cost 
32   ×   33   ×   4 B = 4 224 B per block instead of 4 096 B (+3 %). 
The 33rd column is never read or written. 
4   Both phases stay conflict - free 
Row write: bank = (r + x) mod 32 with x = lane   —   a 
permutation. Column read: bank = (i + c) mod 32 with i = 
lane   —   a permutation.

__global__ void transposeSwizzled(float* odata, 
const float* idata, int rows, int cols) 
{ 
__shared__ float tile[TILE_DIM][TILE_DIM];   // no pad 
int x = blockIdx.x * TILE_DIM + threadIdx.x; 
int y = blockIdx.y * TILE_DIM + threadIdx.y; 
for (int j = 0; j < TILE_DIM; j += BLOCK_ROWS) { 
const int   r =   threadIdx.y +   j,   c =   threadIdx.x; 
tile[r][c ^ r] = idata[(y + j) * cols + x]; // (1) 
} 
__syncthreads(); 
x = blockIdx.y * TILE_DIM + threadIdx.x; 
y = blockIdx.x * TILE_DIM + threadIdx.y; 
for (int j = 0; j < TILE_DIM; j += BLOCK_ROWS) { 
const int   r =   threadIdx.x,   c =   threadIdx.y +   j; 
odata[(y + j) * rows + x] = tile[r][c ^ r]; // (2) 
} 
} 
1   Logical (r, c) → physical column c   ⊕   r 
The tile stays 32   ×   32. Element (r, c) is stored in row r at 
column c   ⊕   r   —   a per - row permutation of the columns. 
2   The same formula reads it back 
XOR is an involution: (c   ⊕   r)   ⊕   r = c, so the store phase 
addresses the element with identical code   —   no inverse 
mapping to maintain. 
3   Row write stays conflict - free 
r fixed, c = lane: c   ↦   c   ⊕   r is a bijection of {0…31} → 32 
distinct banks. 
4   Column read becomes conflict - free 
c fixed, r = lane: r   ↦   c   ⊕   r is also a bijection → 32 distinct 
banks. Zero extra memory.

Why the XOR swizzle works   and is preferred 51 
UW ECE · Graduate GPU Programming · Shared - memory bank conflicts: padding & swizzling 
•   bank( i , j) = (32·i + (j   ⊕   i )) mod 32 =   j   ⊕   i 
•   Fixed row   i   (write): j   ↦   j   ⊕   i   is a bijection of {0…31} → conflict - free 
•   Fixed column j (read):   i   ↦   j   ⊕   i   is a bijection → conflict - free 
•   Involution: (j   ⊕   i )   ⊕   i   = j → store and load share one formula, no inverse 
table   (self - inverse) 
•   Zero extra memory; the row stride stays 128 B, a power of two 
Worked example, logical column j = 5 
lane / row i   0   1   2   3   4   5   6   7 
5   ⊕   i (physical column = bank)   5   4   7   6   1   0   3   2 
(5   ⊕   i)   ⊕   i   5   5   5   5   5   5   5   5 
Row 2 is a permutation of 0…7 (and of 0…31 over the full warp); row 3 recovers the logical column   — 
XOR undoes itself. 
Why production code swizzles 
•   Vector accesses move 16 - byte chunks; a 128 - B 
row holds 8 of them. Swizzle   the chunk index   — 
p = j ^ (( i   & 7) << 2)   —   so each float4 
stays contiguous and aligned . 
•   Padding cannot do this: a 132 - B row stride 
misaligns every row for   ld.shared.v4   and 
ldmatrix . 
•   This is the   Swizzle<B, M, S>   family in 
CUTLASS /   CuTe   (B = 3, M = 2, S = 3 for the case 
above). 
•   Used by   cuBLAS , CUTLASS GEMM, 
FlashAttention   and every tensor - core kernel that 
stages tiles in shared memory.

•   bank =   ⌊ addr   / 4 ⌋   mod 32.   A warp's 32   ×   4 - byte access is one wavefront only if it covers 32 distinct banks (or the same

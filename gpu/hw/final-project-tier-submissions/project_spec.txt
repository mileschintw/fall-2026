1. The project in one page
You will build a standalone inference engine in CUDA C++ that reproduces the forward pass of a pretrained ResNet-18 on
a batch of images and writes classification logits. Nothing from PyTorch, cuDNN, cuBLAS or any other library runs in the
scored path: every kernel is yours. The network has 20 convolutions and every one of them is a GEMM, so the whole
optimization arc of this course (coalescing, shared-memory tiling, bank conflicts, thread coarsening, register tiling, tensor
cores) applies directly, and the leaderboard rewards exactly those skills.
You receive a complete, correct and deliberately naive starter engine, a data pack with the folded weights, preprocessed
images, labels and reference activations, a checker and a submission tool. You deliver a fast engine, a report backed by
Nsight Compute evidence, and a 10-minute presentation. What is scored: correctness (a hard gate), images/s on a T4
(the leaderboard), top-1 and top-5 error, the optimization tier reached, the report and the presentation.
Teams of three. Work on any GPU you like; every leaderboard number is measured on the course's T4 (AWS g4dn.xlarge,
sm_75). Start with GETTING_STARTED.md in the student kit: it takes you from the two downloads to a verified build and
your team's first (smoke-test) leaderboard entry. This document is the reference behind it.

2. The network: ResNet-18 with BatchNorm folded
torchvision's ResNet-18 (He, Zhang, Ren, Sun, Deep Residual Learning for Image Recognition, CVPR 2016; weights
IMAGENET1K_V1) is a 7×7 stride-2 stem convolution, a 3×3 stride-2 max-pool, four stages of two BasicBlocks each, a
global average pool and a 512→1000 fully connected layer. Each BasicBlock is conv3×3 → BN → ReLU → conv3×3 → BN
→ (+ skip) → ReLU; the first block of stages 2–4 uses stride 2 and a 1×1 stride-2 convolution (with BN) on the skip path.
That gives 17 main-path convolutions plus 3 downsample convolutions: 20 in total, 11,684,712 parameters after folding.
BatchNorm folding
At inference BatchNorm is an affine map per channel using the stored running statistics: y = γ · (x − μ) / √(σ2 + ε) + β. The
convolution in front of it is linear, so with s = γ / √(σ2 + ε) the pair collapses into a rescaled filter and a bias: W′ = s · W, b′
= β − s · μ, y = W′ a + b′. The pack ships W′ and b′ (folded in fp32 with ε = 10−5, model in eval mode). There are no BN
layers in your graph; every conv has a bias, and its epilogue is bias → optional residual add → optional ReLU, applied in
fp32 registers before the store.

Conv shape classes
As an implicit GEMM, a convolution computes out[M, N] = A[M, K] × W[K, N] with M = B·H ·W , N = C , K = k·k·C ,

where A(m, k) is a gather from the padded NHWC input (not a copy). All 20 convolutions fall into these classes:

Three things to notice: the stem has K = 147 and the downsample convs K = 64/128/256, which no tile width divides, so
generalized tiling with bounds checks (L4) is required; stage 4 presents only M = 49 rows per image, so batching is how
the T4 gets filled; and every full 3×3 conv costs the same 115.6 MMAC while the GEMM aspect ratio swings from tall to
wide, so one tile configuration will not be best everywhere.


3. The target device and the size of the job
Per image the network costs 3.63 GFLOP (1.81 GMAC). On the T4's 8.1 TFLOPS FP32 peak that is a ceiling of about 2,231
images/s; on the 65 TFLOPS FP16 tensor-core peak about 17,906 images/s. Nobody reaches a ceiling; a well-tuned
SGEMM reaches a large fraction of it, and the starter's direct convolution sits orders of magnitude below. The
leaderboard is scored on the dev set: 500 images, about 1.8 TFLOP per pass (the full val set is 3,925 images, about 14
TFLOP).

4. The data pack
The pack is a directory built once by the instructor; every team uses the same one (checksums.sha256 inside the pack
lets you verify your copy with check.py --verify-pack). Images are the Imagenette validation split (fast.ai's 10-class
ImageNet subset, full-size imagenette2 release), preprocessed exactly as torchvision's IMAGENET1K_V1 transform does
up to the uint8 crop: shorter side resized to 256 (bilinear), center-cropped to 224, stored as uint8 NHWC (RGB).
Normalization — x/255, then (x − mean)/std with mean [0.485, 0.456, 0.406] and std [0.229, 0.224, 0.225] — is the
engine's first op. Labels are ImageNet-1k class indices and the model keeps its full 1000-way head, so top-1/top-5 error is
1000-way. Sets: dev (500 images, 50 per class drawn from val: the scored set, and the one to iterate on), val (3,925
images, the full validation split, for broader testing), debug (8 images, one per class, with per-layer references).

Weights
All folded parameters are concatenated into one blob in op order (filter then bias for each conv and the fc), as float32 in
weights_fp32.bin and as IEEE binary16 in weights_fp16.bin with the same element offsets. Conv filters are stored
[cout][kh][kw][cin] so that the K dimension of the implicit GEMM is contiguous in memory and matches the NHWC
activations; the fc weight is [cout][cin]. Offsets and counts come from the manifest, never from assumptions about
order.

6. The starter engine and the command-line contract
The starter is complete, correct and deliberately naive. It passes the checker as shipped; every kernel in it is yours to
replace. Layout:
 starter/
   CMakeLists.txt            GPU build, sm_75 default; options CPU_EMULATION (no GPU), ENABLE_FP16 (Tier 4)
   include/cuda_compat.h     real CUDA headers or the CPU-emulation layer; LAUNCH(kernel, grid, block, ...)
   include/kernels.h         ConvParams/PoolParams/NormParams, to_f32/from_f32<T>, launch_* declarations
   include/manifest.h        manifest.json -> Op structs (src/manifest.cpp); --print-graph
   include/executor.h        Engine<T>: buffers, batching loop, compute-only timing, outputs, --dump
   src/main.cu               the command line
   src/kernels/normalize.cu uint8 -> normalized T               (one thread per element)
   src/kernels/conv_direct.cu direct conv + fused epilogue      (one thread per output element)
   src/kernels/conv_im2col.cu im2col + naive GEMM + epilogue    (one thread per element, twice)
   src/kernels/pool.cu       maxpool, global avgpool
   src/kernels/fc_topk.cu    fc GEMM; top-5 by five linear scans per image
   third_party/nlohmann/json.hpp

Every kernel is templated on the storage type T (float, or half with ENABLE_FP16) and does its arithmetic in fp32: convert
with to_f32 at the load, accumulate, apply bias/skip/ReLU, convert with from_f32<T> at the store. The starter
instantiates float only; the half instantiations are one macro away. The tensor-core kernel (Tier 4) is a new kernel body
that reuses the gather index math, the epilogue and the launcher, not a half instantiation of the SIMT kernel.

Command line
 engine --pack DIR --set {val|dev|debug} --out OUTDIR [--batch B] [--precision fp32|fp16]
        [--conv direct|im2col] [--iters N] [--warmup W] [--dump] [--print-graph]

 output                     format
 logits.bin                 count x 1000 float32, image order of the set; logits (pre-softmax), always fp32.
 top5.bin                   count x 5 int32, descending by logit, lowest class index first on ties.
 timing.json                device, precision, batch, per-iteration ms, median ms, images_per_s, emulation flag.
 dump/<tensor>.bin          With --dump (set must fit in one batch): every manifest tensor except image_u8, count x [shape], float32 (top5
                            int32).
Timing rule: Compute only. All images are resident on the device before the clock starts; the timed region runs from the
first normalize kernel to the last top-k kernel over all batches; D2H happens after. 1 warm-up iteration, then --iters timed
iterations; the median is reported.
The grader passes only these arguments: --pack, --set, --out, --batch (yours, from submission.json), --precision (your
category), --iters, --warmup, plus any extra arguments you declare in submission.json (for example --conv igemm to
select your own conv path). Everything else, including the default conv mode, is your engine's business.

7. Correctness: the per-layer check and the leaderboard gate
Per-layer references were produced by running the folded PyTorch model on the debug images and recording every
tensor in the manifest (conv outputs post-bias and post-ReLU as the graph defines them, block outputs post-residual).
check.py --layers runs your engine with --dump on the debug set and compares each dump/<tensor>.bin with
ref/<tensor>.bin, so a bug in one kernel is isolated from error accumulating across 18 layers. Use it before and after
every change.
 check                                                   fp32                                      fp16 reduced precision
 per-layer max|err| / max|ref| (debug set)               ≤ 0.001                                   ≤ 0.02
 top-1 agreement with the reference logits               ≥ 99.5%                                   ≥ 99.5%
 top-1 and top-5 error vs. labels                        within ±0.5 pp of the reference           within ±0.5 pp of the reference
 top5.bin consistent with your own logits (tie rule)     100% of rows                              100% of rows
 all logits finite                                       yes                                       yes
Why these numbers: an fp32 CUDA implementation differs from PyTorch only by summation order, so per-layer error of
         −6                                                  −3
about 10 relative is normal and logits agree to about 10 ; top-1 agreement should be 100%. An fp16 path lands
           −3      −2
around 10 to 10 on logits and above 99.5% agreement. The gate is therefore agreement plus a tolerance, not bit
equality. A run that fails any line of the gate is not posted to the leaderboard at all: a fast wrong kernel scores zero.
Categories
 category                      rule                                                                    roofline ceiling (images/s, T4)
 FP32                          single precision end to end                                             2,231
 FP16 reduced precision        fp16 operands anywhere (tensor cores or not), fp32 accumulation;        17,906
                               logits in fp32
A team may hold a position in both categories. Using fp16 operands anywhere in the network (with or without tensor
cores) places the run in the reduced-precision category; accumulation must be fp32 and the logits are written in fp32.


8. Leaderboard, submissions and rules
Each submission is graded on the same g4dn.xlarge T4 image with the course nvcc for sm_75, one submission at a time:
unzip, static scan for forbidden libraries, cmake build, per-layer check on the debug set, a timed run on the dev set (500
images; 1 warm-up pass, then 3 timed passes, of which the median is reported) while nvidia-smi samples the SM clock,
then the end-to-end gate on the same set. Every round, from the Tier 0 smoke test to the freeze, uses this same
protocol, so all entries on the board are directly comparable. You can reproduce the timed run on your own GPU with
check.py --set dev --iters 3 --warmup 1.
The leaderboard is published in two views built from the same results. The overall view ranks valid runs by images/s
within each category. The by-tier view groups each category by tier, highest first, and ranks by images/s within the tier,
keeping the overall rank as a column. Both include a secondary efficiency ranking (images/s as a fraction of the
category's roofline ceiling, so a well-tuned fp32 engine is recognized next to a tensor-core engine) and a list of invalid
submissions with the reason. Each team is represented by its best valid run. The tier shown is the one you declare with
submit.py --tier; the staff verify tiers against your design specification and report and may reassign them, in which case
the board marks the tier as verified.
After each grading round every team receives a short report for each submission: for a valid run the measured figures;

Rules
Allowed in the scored path: CUDA runtime, streams, events; cooperative groups; warp intrinsics (shuffle, vote, match);
WMMA and mma.sync (inline PTX) tensor-core instructions; cuda_fp16.h conversions. Any GPU for development; the
score is the T4's.
Not allowed in the scored path: cublas, cudnn, cutlass, cub/, thrust, torch, onnxruntime, nvinfer, tensorrt, any
framework or vendor inference library, and precomputed outputs of any kind. The checker and the reference use
PyTorch; that is fine.
The scan is a strict text search. The grader searches every source and CMake file in your submission, line by line and
case-insensitively, for the identifiers above, and rejects the submission on any match. It does not parse code: a match in
a comment or a string counts exactly like an #include or a call. Do not mention these names anywhere in your sources,
not even in a comment such as "faster than ...". The report for a rejected submission lists the file and line of every match.
The grader builds for sm_75 only. Instructions the T4 lacks (cp.async, bf16, the m16n8k16 fp16 MMA shape, wgmma,
thread-block clusters) fail to assemble there even if they ran on your own GPU. Keep 75 in your architecture list so you
see the failure first.
